MISSION
Implement the complete engineering scope ZV-00 through ZV-35 in dependency order: a separately versioned, deterministic, offline Prax Visual Lab runtime; no-API and no-network safeguards; capability-adaptive harness-neutral execution policy; versioned lesson and receipt schemas; accessible state-stepper, parameter-lab, compare-views, hint engine, and receipt panel; Python floating-point, Rubik’s move, and lost-update laboratories; one explicitly measured Lean build-time experiment; evaluation machinery; exact-byte review, verification, documentation, candidate packaging, rollback, and truthful handoff.

Preserve the current bundled Markdown renderer and host-chat route as the universal static fallback. Do not turn ChatGPT/Codex subscription access into a programmatic backend. The runtime must work without any model, API, cloud, telemetry, CDN, remote font, or network request.

NORTH STAR
The learner can later retrieve, explain, apply, discriminate, and transfer the idea without the tutor—and the system can show honest evidence for that claim.

TRUTHFUL TERMINAL STATES
1. Emit ENGINEERING_COMPLETE / SCIENTIFIC_EVIDENCE_PENDING only after every engineering criterion ZV-00..ZV-35 is independently recomputed as verified on one exact clean HEAD while one or more external gates remain unverified.
2. Emit UPGRADE_100_PERCENT_VERIFIED only after the same engineering closure AND genuine EG-ZV-01..EG-ZV-04 accessibility, immediate, elapsed 7–14 day, and novel-transfer observations pass the frozen protocol.
3. Never substitute synthetic learners, fixtures, agent judgments, automated accessibility checks, a planned delay, or generated receipts for external human evidence.
4. If external participants or elapsed time are unavailable, finish all engineering and study-preparation work, park those exact external gates as waiting_external, and report the precise unblock. Do not call that scientific completion.

AUTHORITY AND PROHIBITIONS
- You may inspect and modify the candidate repository and the plan/tracker artifacts within the working root.
- You may create a dedicated local branch or isolated worktree, add project-scoped pinned open-source dependencies, download project-local browser/test binaries when policy permits, run tests/builds/browsers, create local commits after gates pass, and create a local candidate archive and receipts.
- Preserve unrelated dirty state. If overlapping user changes exist, inspect, isolate, and integrate safely; do not discard them.
- Never use an API key, API-billed model, OpenRouter, provider SDK, metered model endpoint, browser automation of ChatGPT, hidden subscription scraping, telemetry, remote runtime asset, CDN, or cloud learning backend.
- Never read, print, transmit, or copy secrets or unrelated private learner data.
- Do not modify global configuration or global dependency state.
- Do not merge, push, deploy, publish, install/replace the canonical skill, recruit/contact external participants, spend paid credits, or delete material data without an explicit human approval at that action.
- A passing test never broadens these permissions.

CAPABILITY-ADAPTIVE EXECUTION
Describe required roles and evidence, not provider-specific commands.
1. At the beginning of each iteration, inspect tools and governing policy exposed by the current harness.
2. Use the primary agent by default.
3. Delegate only genuinely independent work whose expected benefit exceeds quota and coordination cost.
4. Prefer authorized native delegation. Use at most two native subagents concurrently, depth one, with bounded ownership, read/write scope, evidence, and stop conditions. Workers must know others may edit the tree and must not revert others.
5. Default external agent CLI calls to zero. An already-installed subscription-backed CLI is an optional fallback only after checking current help, authentication mode, permission, working directory, quota impact, noninteractive behavior, output capture, and user authorization. Use at most one CLI delegate at a time and at most two total in the entire goal. Never use it when auth or cost is uncertain. Never recursively delegate from it.
6. Do not convene a broad council. One bounded independent architecture review may be used at the final phase if native capability exists and budget remains.
7. The primary agent always owns synthesis, integration, learner-safety, accessibility, privacy, tests, evidence, and the final claim.
8. If delegation is absent, disallowed, or unnecessary, continue single-agent without lowering the bar.

COST AND LOOP BUDGET
- One primary agent; no more than the delegation limits above.
- Work on exactly one acceptance atom per implementation iteration.
- Stop the same failing approach after three attempts. Preserve complete failure output and side information, diagnose, then reroute instead of repeating it.
- At most two review-repair rounds per phase unless a new failing test provides materially new evidence.
- Do not invoke another model merely to restate, summarize, or rubber-stamp work.
- Prefer focused tests while iterating; run phase and full gates at declared boundaries.
- If subscription/quota telemetry is available and shows unsafe remaining capacity, stop optional delegation and continue primary-agent work. Do not consume API credits.

Before code changes:
1. Read the entire canonical plan and tracker.
2. Re-inspect the current repository root, AGENTS.md or equivalent instructions, branch, HEAD, dirty state, dependencies, tests, current static route, and relevant source. Treat all prior status as a snapshot.
3. Create or refresh these durable files inside the candidate:
   .agent/zero-api-visual-runtime/SPEC.md
   .agent/zero-api-visual-runtime/prd.json
   .agent/zero-api-visual-runtime/progress.txt

4. SPEC.md must incorporate the original plan’s constraints, architecture, North Star, acceptance ledger, external evidence boundary, and promotion gates. It may clarify but may not silently weaken them.
5. prd.json must contain one independently verifiable atom for every ZV and EG-ZV criterion, using observable EARS-style acceptance conditions, dependencies, status, evidence paths, and retry count.
6. The JSON tracker in outputs remains the authoritative cross-task status. Keep SPEC/prd/tracker IDs aligned. Markdown and HTML tracker files are generated views, never competing hand-authored state.
7. Append progress and audit entries; never erase failed attempts or rewrite history to look clean.

EXECUTION DAG
Phase 0: ZV-00..ZV-05 — freeze/current audit, runtime ADR, no-API/no-network contract and tests, capability-adaptive policy, schemas, static baseline.
Phase 1: ZV-06..ZV-13 — runtime scaffold, state-stepper, receipt panel, ordered hints, Python floating-point pilot, static/no-script/reduced-motion paths, browser/accessibility/privacy/security gates, independent stop/go review.
Phase 2: ZV-14..ZV-21 — parameter-lab, compare-views, shared hint/grader limits, deterministic builder/manifest, Rubik’s lab, lost-update lab, cross-domain reuse proof, full MVP verification.
Phase 3: ZV-22..ZV-25 — one Lean ADR, pinned build-time adapter, proof-state lesson/static equivalent, measured keep-or-revert decision. Rejection is acceptable if the declared threshold is not met and cleanup is verified.
Phase 4 engineering: ZV-26..ZV-29 — frozen evaluation protocol, capture/analysis machinery, accessibility field protocol, immediate/delayed/transfer operations.
Phase 4 external: EG-ZV-01..EG-ZV-04 — real observations only; otherwise waiting_external.
Phase 5: ZV-30..ZV-35 — gated optional integrations, Markdown/HTML parity, independent exact-byte reviews, clean-room full verification, immutable candidate/rollback package, truthful promotion handoff.

ONE-ATOM AUTONOMOUS LOOP
Repeat until no unblocked engineering atom remains:
1. Re-read SPEC.md, prd.json, progress.txt tail, tracker JSON, current git status, and latest relevant evidence.
2. Reconcile drift. Never trust a stale PASS, hash, test count, dependency version, or browser result.
3. Select the highest-priority dependency-unblocked engineering atom. Mark only it in_progress and record owner/start state.
4. Write the smallest coherent implementation and regression fixtures for that atom. Do not perform speculative adjacent refactors.
5. Run focused tests. Capture full commands, exit codes, versions, and complete failure output.
6. On failure, diagnose root cause and repair. After three failures of the same approach, record side_info and choose a materially different route. Do not loop blindly.
7. Run the atom’s negative, accessibility, privacy/security, no-network, deterministic, or property gates as applicable.
8. Review the exact diff against the original plan, current criterion, architecture boundary, answer-leakage rules, fallback, and claim policy. Use an independent bounded reviewer only when it materially helps and is within budget.
9. Fix every critical/high finding and all in-scope medium findings. Rerun affected focused gates.
10. Run the current phase gate when an exit boundary is reached. Do not rely only on focused tests.
11. Attach exact evidence to prd.json and tracker JSON; append progress and audit records; regenerate tracker Markdown/HTML; validate their consistency.
12. Make a scoped local commit only after the atom/phase gates and review are green. Include criterion IDs in the commit message. Do not commit unrelated files.
13. Start the next iteration from durable state. Use a fresh context when the harness supports it; do not depend on conversational memory.

IMPLEMENTATION REQUIREMENTS
- Use TypeScript plus standards-based Web Components unless the current-tree audit demonstrates a better lower-complexity fit. Avoid a framework by default.
- Keep runtime code separately versioned and removable. Preserve fail-closed static routing when it is missing, incompatible, or unverified.
- Use native semantic controls and a deterministic state model. Essential meaning must survive JavaScript-off, print, and reduced-motion routes.
- Components: state-stepper, parameter-lab, compare-views, ordered hint-engine, receipt-panel.
- Lessons: Python floating point, Rubik’s legal move/permutation model, concurrency lost-update interleavings.
- Use exact/structural graders only where correctness is deterministic. Route ambiguous natural-language interpretation to the human-operated host tutor.
- Receipts must be versioned, local, inspectable, copyable, downloadable, import-validated, migratable when supported, and deletable. No silent transfer.
- Enforce CSP and automated no-network interception. Reject telemetry, remote assets, dynamic remote imports, service-worker updates, and API-key configuration.
- Pin project dependencies and record provenance. No floating deterministic build commands.
- Lean is build-time only, pinned, and one experiment. Export proof-state JSON and a formal receipt; do not put a live theorem prover in the learner artifact. Keep or remove it by the declared evidence threshold.
- SkillOpt and Flint remain optional and off by default. Use them only after a frozen benchmark names a real job and the adapter beats baseline without violating a hard gate.
- TLA+, Alloy, Dafny, Agda, F*, VR/AR, gamified streaks, and an embedded AI chatbot are out of scope.

TEST AND REVIEW BAR
Maintain one reproducible verification entry point that fails closed. Include:
- schema positive and adversarial negative fixtures;
- unit tests for reducers, transitions, hints, graders, receipt operations, import failures, deletion, and migrations;
- property tests for state reachability, cube invariants, interleavings, receipt round trips, and idempotent builds;
- integration tests from lesson spec to artifact to receipt and from formal receipt to proof-state artifact;
- browser tests for current Chromium, WebKit/Safari behavior on macOS, and Firefox when available;
- keyboard-only, focus, names/roles, announcements, contrast, 200%/400% zoom/reflow, reduced motion, JavaScript-off, print, and screen-reader walkthrough evidence;
- CSP, injection, dependency, storage, privacy, corrupt-import, secret-scan, and no-network tests;
- two clean builds with identical declared output and manifests;
- preservation tests for the existing static renderer and router fallback;
- independent exact-payload code, architecture, pedagogy, accessibility, privacy/security, and claim review;
- a clean-room final rerun. A missing environment is UNVERIFIED, never PASS.

REVIEW BEFORE COMMIT
Before each local commit:
1. inspect git diff and status in full;
2. map every changed file to an active criterion;
3. run focused and required phase tests without truncating state-changing output;
4. perform the bounded code-review/fix/rerun loop;
5. ensure no secret, API path, remote runtime dependency, stale generated file, or unsupported claim entered;
6. update exact evidence and tracker views;
7. commit only the scoped green change.

FINAL VALIDATOR
After all reachable engineering atoms appear complete, start from the original canonical plan—not from the implementation summary—and independently verify every ZV-00..ZV-35 acceptance condition against the same clean HEAD and package bytes. Recompute hashes, tests, builds, browser matrix, docs parity, receipts, static rollback, and known limitations. Reject stale or self-referential evidence. Reopen any failed criterion and continue the loop.

COMPLETION RECEIPT
The final handoff must include:
- exact repository root, branch, HEAD, clean/dirty state;
- engineering count and external count separately;
- criterion-by-criterion status and evidence paths;
- commands, versions, test totals, browser matrix, hashes, and package path;
- architecture and privacy/no-network evidence;
- Lean keep/revert decision and rationale;
- optional integration decisions;
- unresolved findings and external gates;
- rollback instructions;
- the precise user approvals still required for merge, push, deploy, or canonical installation.

Do not stop at code generation. Continue implementing, testing, reviewing, fixing, rerunning, documenting, packaging, and independently validating until every reachable engineering criterion is actually verified or a genuine external/human authorization gate is precisely parked. Never claim more than the evidence proves.

Expected autonomous result

The command deliberately separates autonomous implementation from irreversible promotion and from scientific claims. A correct agent should continue through the entire engineering DAG, preserve an audit trail across fresh contexts, and stop only at:

  • a fully verified local candidate plus a precise external-study handoff;
  • an explicit human authorization gate;
  • or a real, evidenced blocker after bounded alternative routes have been exhausted.

It must not burn quota on broad councils, repetitive reviews, or model-to-model restatement.
